Automating the Accounts Payable workflow with an AI agent

Today, each client's monthly AP run is done by hand: checking invoices against payment listings, verifying staff claims against policy, rolling forward spreadsheets, and filling in the Maybank file. This design has an AI agent do the reading and cross-checking — while people keep every decision that moves money. The agent runs only when a person starts it, and it never edits the working files: it prepares copy-ready output for a person to paste in.

1Today vs. proposed

The work doesn't change — who does the repetitive part of it does.

Today — manual

  • Download email attachments, unzip, save to SharePoint by hand
  • Ctrl+F each invoice number in the year's payment listing
  • Check every staff claim one by one against the policy sheet
  • Roll the payment listing forward, rename files with running numbers
  • Copy-paste amounts into the Maybank bank file, reconcile totals

Proposed — agent-assisted

  • You hand the batch to the agent; it reads every document in one run
  • Agent fetches the listing & policy sheet itself (read-only) and looks up every invoice; exceptions flagged, not hidden
  • Claims checked against policy limits; over-limit items surfaced
  • Listing rows and bank-file entries prepared in the exact format — ready to copy & paste
  • A person reviews the flags and approves — before anything is paid

2The monthly pipeline

Example: a client sends one zip file containing a month of invoices and staff claims, including scanned images. A colleague starts a run and hands that zip to the agent — nothing runs in the background waiting for files. Each stage is labelled by who does the work — the AI, plain software rules, or a person.

  1. 1
    Software

    Intake & gather context

    You start a run and give the agent the month's files — the client's zip, dropped straight into the app. The agent unpacks it in a private working area, then fetches the reference documents it needs — this year's payment listing, the client's policy sheet, last month's files — by reading the client's SharePoint folders. It never writes anything back to SharePoint.

    In: 1 zip file + client name  →  Out: 47 documents to sort, plus the listing & policy sheet fetched for reference.
  2. 2
    AI

    Sort the pile

    The AI looks at each document — including scans and photos — and answers one narrow question: is this an invoice, a staff claim, or a receipt that belongs with a claim?

    Out: a manifest — 31 invoices, 12 claims, 4 receipts attached to claims.
  3. 3
    AI

    Read each document

    For every invoice: vendor, invoice number, date, amount, currency. For every claim: claimant, expense type, amount, and its receipts. One document, one focused question — the pattern where AI reading is most reliable.

    Out: a structured table of every document's details, with a confidence note per field.
  4. 4
    AI Software

    Run the checks — judgment by AI, arithmetic by code

    Policies are rarely just numbers, so this stage is a partnership. The AI does the judgment calls: which expense category does this claim belong to, which policy clause applies, does "Maxis Broadband" mean "Maxis Bhd"? Every AI judgment must cite the policy line it relied on, and "not sure" becomes a flag, never a pass. Then plain code does what code does best: invoice-number lookups in the listing, date comparisons, limit arithmetic, totals reconciliation — repeatable and free to re-run.

    AI: "team lunch" receipt → staff welfare, not client entertainment, per policy §4.2 → cap applies. Code: $95 > $80 cap → flagged. Code: invoice not found in listing → flagged.
  5. 5
    Person

    Review & approve

    The agent presents everything inside the app: one flag report, proposed file names, draft payment-listing rows, and draft bank-file entries. A colleague resolves the flags and approves — then copies each approved block into the real working documents. Nothing is written to SharePoint or any working file by the agent, and nothing proceeds to payment without this step.

    "31 invoices: 28 clean, 2 not in listing, 1 dated January. 12 claims: 10 within policy, 2 over limit."

3Inside the agentic loop

An AI model can only read text and reply — it can't touch files by itself. The "agent" is a conversation loop our application runs around the model. Here is one turn of that loop, and a real trace of it processing a staff claim.

  1. The app sets the table. It sends the model the task ("check this claim against Client ABC's policy") plus a menu of tools it may ask for: read a document, look up the payment listing, search a folder.
  2. The model asks, it never acts. It replies with a request: "run read_document on claim_07.jpg". It cannot run anything itself.
  3. The app does the work. Our own code executes the tool — opens the file, runs the Excel lookup — and sends the result back into the conversation.
  4. The model decides the next step based on what came back: ask for another tool, or finish.
  5. The loop ends with structured output, not prose: a table of extracted fields and flags that our checking code and the review screen consume.
Steps 2–4 repeat until the task is done — typically 2–4 turns per document, not dozens.
Trace — one staff claim, start to finish agent → read_document("claim_07.jpg") tool ← {claimant:"Tan W.L.", type:"wi-fi", amount:95.00, currency:"USD"} agent → category: "home wi-fi" → Telecoms, basis: policy §4.2 "internet subsidy" agent → policy_lookup("ABC", "telecoms") tool ← {cap:80.00, currency:"USD"} code check: 95.00 > 80.00 → OVER_LIMIT agent → final: {status:"flagged", reason:"wi-fi $95 exceeds $80 cap (§4.2)", evidence:"claim_07.jpg"}   → appears on review screen as flag #2

The key design choice: the routine path is scripted, not agentic. The pipeline order — intake, sort, read, check, review — is fixed in ordinary code. The AI loop only runs inside the stages that need judgment (reading documents, resolving fuzzy vendor names). A free-roaming agent that "figures out" the workflow each month would be slower, less predictable, and roughly 10× more expensive. This one choice is also our biggest cost control.

4Keeping the cost down

AI usage is priced per token — roughly, per word or image-patch the model reads and writes. Four levers keep the bill small; LiteLLM (the AI switchboard — in the enterprise, the shared company proxy with its approved model catalogue) makes the first two a configuration choice, not a rebuild.

Right-size the model per stage

Sorting a document into "invoice / claim / receipt" is easy — a small, cheap model does it well. Full extraction gets a mid-tier model. The largest models are reserved for the few documents flagged as low-confidence. Same pipeline, three price tiers.

Typical saving: 60–80% vs. one big model for everything
AI only where judgment lives

Invoice lookups, date checks, limit maths, and totals reconciliation run as plain code — cost: zero, and re-running them is free. The AI's judgment work (expense categories, which policy clause applies) runs over the small extracted text table, not the images — a fraction of the reading cost. Each document is read by AI exactly once; results are saved, so nothing is ever paid for twice.

Code checks & re-runs: $0 · judgment pass: cents
Send less to the model

Scans are downsized before sending — a receipt doesn't need to be a 12 MB photo. The payment listing never goes to the model at all: our Excel tool sends back only the one row a lookup finds, not thousands of rows.

Cuts the per-document token bill by half or more
Cache the repeated parts

The instructions and client policy sheet are identical for all 47 documents — prompt caching means we pay full price once, then a fraction for each reuse. Whether caching (and any bulk-pricing) discounts pass through the enterprise proxy is one of the things to confirm in enterprise testing.

Caching: up to 90% off repeated context — to verify via the proxy

6How the pieces connect

The agent runs inside our own application. It reads SharePoint through a ready-made, read-only connector, and reaches AI models through one switchboard — so we are never locked to a single AI provider.

SharePoint Client folders, payment listings, policy sheets, historical files
↓
MCP connector — a pre-built, maintained bridge that searches sites, lists folders, and fetches documents. Read-only by design — it cannot change anything in SharePoint. Each user signs in with their own account; sign-in and credentials live in the server layer and are never shown to the AI.
↓
Agent application Runs the pipeline when a user uploads a batch · owns the tools: unzip, Excel lookup, document reading, template-to-output formatting · one config file per client (paths, policy limits, funding style)
↕
LiteLLM — one switchboard to AI models. In the enterprise this is the shared company proxy with its approved model catalogue; on a development machine it can point at providers directly. Same application either way.
↕
AI models Read documents & images, answer narrow questions — no direct access to files or payments
↓
Copy-ready output → person pastes & approves Flag report, listing rows, bank-file entries — shown in the app for a person to copy into the real documents. The human gate before any payment step.

7Design principles

AI reads and judges, code does the math, people decide

The AI extracts information and makes the judgment calls — expense category, which policy clause applies — always citing the policy line it relied on, so a reviewer can verify the reasoning. Code does the arithmetic and lookups, repeatably. People resolve flags and give approvals.

The human gate is permanent

The agent never edits a working document, never uploads a bank file, and never triggers a payment. Its output is always something a person copies into place. That is a design rule, not a temporary limitation.

One pipeline, many clients

Client differences — folder locations, policy limits, funding model, file-naming rules, output templates — live in a one-page config file per client plus an uploaded template. Onboarding a client means writing a config and uploading their formats, not building software.

Portable by construction

All file access goes through one swappable layer. Development happens on a Mac against sample files; the pilot runs on a Windows machine with the enterprise proxy and read-only SharePoint connector; moving to Azure later swaps that one layer, not the application.

8Delivery roadmap

Built in thin slices, each useful on its own. Slice 1 changes nothing — it only reports — which is how we build trust before automating more.

SliceWhat it doesRisk profile
1 · Invoice checking Reads a batch, extracts details, looks up every invoice in the payment listing, produces the flag report. Read-only — changes no files, touches no money.
2 · Claims vs. policy Checks staff claims against each client's policy sheet; currency and limit flags. Read-only — same reporting pattern.
3 · Listing roll-forward Prepares copy-ready listing rows, vendor groupings, and proposed file names with running numbers. Copy-paste only — a person pastes rows into the workbook.
4 · Maybank entries Learns the bank format from an uploaded template, builds copy-ready entry rows, reconciles totals. Copy-paste only — a person always pastes, reviews, and uploads.
5 · Azure hosting Moves the proven pipeline from the pilot machine to Azure; adds schedules and monitoring. Infrastructure change only — pipeline behaviour already proven.

9Assumptions to validate in the enterprise environment

This design is being built on a development machine against sample files; testing happens in the Windows enterprise environment. These are the assumptions the design depends on, and how each gets validated there.

AssumptionBasis todayHow we validate
SharePoint read access is enough The read-only MCP connector was probed successfully: site search, folder listing, document metadata, and workbook download all worked with a user's own sign-in. Copy-paste output means no write access is ever needed. Re-run the probe against the real AP client folders; confirm the listing and policy sheets are reachable. Note: occasional connector errors were seen — retries succeed, so the app needs simple retry logic.
Sign-in lasts a full run The saved sign-in session was shown to be reused without re-prompting. A run starts only when a user is present, so a mid-run expiry simply pauses with a "reconnect" message — never a surprise browser popup. Time a full 47-document run against a live session; confirm the reconnect path behaves.
Model tiering works on the proxy All AI calls go through the shared enterprise proxy and its approved model catalogue. The catalogue has multiple tiers, so cheap-sort / mid-extract still applies. Map each pipeline stage to a catalogue model; confirm caching or bulk discounts pass through, and re-cost the batch table.
Template-to-output formatting is reliable Built and tested here with sample Maybank and listing templates. Paste the generated rows into the real workbook and bank portal on the pilot; confirm columns, codes, and totals land correctly.

10What we need to start

From IT: approval for an AI service on client data through the shared enterprise proxy, and read-only SharePoint access via the existing connector — each user signs in with their own account, and the app can never modify SharePoint. No write access is requested.

From the AP team: one client to pilot with, their policy sheet, a copy of the Maybank template and payment listing layout, and an hour to agree what a useful flag report looks like.

Decision needed: confirm the human-approval line stays exactly where this design puts it — the agent prepares, a person pastes, and nothing is paid without a person's approval.
